# Somaplus architecture

Somaplus is a school management system for East African schools, built by Odessa Lab Technologies. One codebase and one database serve many schools; each school is a tenant. Rules for contributors live in `CLAUDE.md`; this file explains the structure behind them and is updated whenever the structure changes.

## Repository layout

| Path | Purpose |
| --- | --- |
| `public/assets/` | Static files of the purchased UI template (CSS, JS, plugins, fonts, images). Served as-is. |
| `resources/template-original/` | The template as supplied, except `assets/`: its 64 static HTML pages (62 pages plus login and register), its `README.md`, the `tools/` scripts that produced the pages, and `laravel/`, the Blade version of the same pages (layout, header, sidebar, one view per page, `routes/somaplus.php`). Reference only; never served and never edited. |

## Template boundary

The template is a purchased asset and stays exactly as supplied.

- Files under `public/assets/` and `resources/template-original/` are never edited, renamed, minified or modernized. Both folders are an exact copy of the `somaplus/` folder of `Swai-D/merge-temp` at commit `b716aa1` (the final template: 537 files), verified file by file with sha256. To take a newer version of the template, replace both folders with the new supplied files and verify again the same way.
- Product behaviour is added by Blade wrappers that include the template's assets and copy its markup. If something needs different styling, it goes in a new stylesheet, not in a template file.
- The application's own files live outside the template: `public/css/somaplus-app.css` holds the few rules the application needs on top of the template, and `public/img/somaplus-logo.svg` (and its white version) is the logo of the application. The template's own `logo.svg` is not used: its wordmark is drawn as text in a canvas that is just wide enough for one font, so a browser that picks a wider font cuts the last letter off. Our logo pins the width of the wordmark (`textLength`), so the name always reads "SomaPlus". The icon of the collapsed sidebar still comes from the template (`logo-small.svg`), because it holds no text.
- The UI stays on the template's Bootstrap and jQuery. Tailwind is not used (the Laravel default was removed); Vite only builds `resources/js/app.js`.
- `resources/template-original/tools/*.py` are the template author's build scripts. They are kept for reference and are not part of the application.
- The supplied `laravel/` package is a UI-only mock: every page is static markup with made-up data, mounted with `Route::view`, with no login, tenant or permission checks. It is not copied into `resources/views/` or routed as it is, because school users would see fake students and fees. Our own wrappers in `resources/views/` reuse its markup, and a page gets a route only together with the feature that gives it real data.

## Tenancy

One school is one tenant, in a single database. Tenant ids are ULIDs.

- **Resolving the tenant.** `App\Http\Middleware\ResolveTenant` runs first in the `web` group and picks the tenant from the request host (`config/tenancy.php`): a host in `central_domains` has no tenant (the super-admin area); a tenant's own `domain` matches exactly; otherwise `<slug>.<base_domain>` matches the school with that slug. Any other host is a 404. There is deliberately no header override. The one exception is the **Railway path entry** for hosts with no wildcard subdomain (`*.up.railway.app`), off unless `TENANCY_ALLOW_PATH_ENTRY=true`: `GET /t/{slug}` on a central host remembers the school in the browser session, and `ApplyPathEntryTenant` (appended to `web`, and placed after `StartSession` and before authentication/route binding with `appendToPriorityList`) sets that school as the tenant on central hosts only. It cannot override a school's own address, it never reads a header, the user lookup stays scoped to that school (another school's users cannot sign in through it), and sign-out keeps the chosen school. Switch it off once the school has its own domain.
- **Context.** `App\Tenancy\TenantContext` holds the current tenant. It is bound as a scoped instance, so nothing survives between requests or queued jobs. Use `TenantContext::run($tenant, fn () => ...)` for work on behalf of one school; the previous context is restored afterwards, even on an exception.
- **Tenant-owned models.** Add the `App\Models\Concerns\BelongsToTenant` trait and a `tenant_id` ULID column (`foreignUlid('tenant_id')->constrained('tenants')`, no cascading delete: a school's data is never removed because of a subscription change). The trait applies `TenantScope` to every query, fills `tenant_id` on create, and refuses to write a row for another tenant or to move a row between tenants (`TenancyViolation`).
- **Fails closed.** With no current tenant, a scoped query returns nothing and creating a row throws. The only way to see every school's rows is `TenantContext::runAsSystem(fn () => ...)`, reserved for reviewed super-admin and system operations; every call needs a reason in code review.
- **Queued jobs.** A job that touches tenant data uses the `App\Tenancy\TenantAwareJob` trait: dispatch it with `->forCurrentTenant()`; only the tenant id is serialized, and `RestoreTenantContext` job middleware reloads the tenant and runs the job inside it. A job without a tenant id fails.
- **Users** are the one tenant-owned model that does not use `BelongsToTenant`; see below.

## Users, roles and permissions

- **Users.** `users.tenant_id` points at the school; a super-admin (`is_super_admin`) belongs to the platform and has no school. `UserScope` shows a school only its own users, the central domain only super-admins, and everything only inside `TenantContext::runAsSystem()`. A normal user always has a school (taken from the current tenant when created); a super-admin cannot be created inside or for a school; a user cannot be moved to another school or promoted to super-admin afterwards. `tenant_id` and `is_super_admin` are not mass assignable. The email address is unique per school, not globally, so one person can sign in at two schools. Password reset tokens are per school, see Sign-in below.
- **Roles.** `spatie/laravel-permission` runs in teams mode, where the team is the school (`permission.team_foreign_key` is `tenant_id`, a ULID that cannot be null). `TenantTeamResolver` always answers with the current tenant and refuses to be set to anything else, so a role check can never be answered for another school. Roles and role assignments belong to a school; permission names are shared rows.
- **The five roles** are in `config/roles.php` (`owner`, `head_teacher`, `teacher`, `accountant`, `parent_student`), with English and Swahili labels in `lang/*/roles.php`. Every new school gets all five (`Tenant::created` runs `SyncTenantRoles`). Syncing is idempotent and only adds; it never revokes.
- **Permissions** are added to `config/roles.php` only together with the feature that checks them (`'students.view' => ['owner', 'teacher']`). Existing schools receive a new permission by running `SyncTenantRoles` for each school (a data migration), because the config is seed data and not the source of truth.
- **Assigning roles.** Assign by name or id (`$user->assignRole('teacher')`), inside the school's context. `User::assignRole()` refuses a `Role` object of another school, which the package does not check by itself. Do not assign roles outside a tenant context.
- Super-admin permissions arrive with the super-admin area.

## Sign-in, language and layout

- **Sign-in.** `GET/POST /login` (`LoginController`, `LoginRequest`, `App\Domain\Auth\AttemptLogin`). Who can sign in where is decided by `UserScope`: on a school's address only that school's users are found, on the central address only super-admins, so there is nothing to compare by hand and no way to sign in to another school. Five failed attempts per email, address and host block further attempts for a minute. The session id is regenerated on sign-in; `POST /logout` invalidates the session but keeps the chosen language. Sessions are host-only cookies, and a session of one school is not valid on another because the user is looked up through the scope. Sign-in and sign-out do not use `tenant.writable`.
- **Password reset.** `GET/POST /forgot-password` and `GET /reset-password/{token}`, `POST /reset-password` (`SendPasswordResetLink`, `ResetPassword`, Laravel's password broker; these are guest routes and never use `tenant.writable`). The person is looked up through `UserScope`, so only someone of the school at that address (or a platform administrator on the central address) can be found. `User::getEmailForPasswordReset()` returns a hash of school and email, which is the key in `password_reset_tokens`, so the tokens of two schools never meet even for the same address; the link itself carries the plain address. The forgot-password page always answers the same message, so it cannot be used to find out who has an account. Links last 60 minutes and work once; the email (`ResetPasswordNotification`) is in the language of the person asking and links to the address the request came from. Sending needs a working mail setup (`MAIL_*`; Mailpit locally).
- **Dashboard.** `GET /` (`dashboard`, behind `auth`) shows only real data (`BuildDashboardSummary`), laid out like the template's `index.html` (coloured tiles, a bar chart, progress bars, short lists) and drawn with the template's bundled ApexCharts. The "Your school" card holds the name, plan, subscription state (with the end of the grace period), current year and term, and the person's roles; the central address shows the number of schools. `SchoolDashboardFigures` adds the figures, each one only when the person holds the permission that guards its own page: students (active count, admitted this month), guardians, recent admissions, the people of the school (pupils, teaching accounts, staff accounts) and the pupils of each class need `students.view`; classes `academics.view`; fees for the school's current academic year (invoiced, collected, outstanding, the twelve-month chart, recent payments) need `fees.view`; today's attendance split by status and the register of the last thirty days need `attendance.manage`; the best pupils of the last locked exam need `results.view`. Reversed payments are left out, an overpaid invoice never reduces what another invoice owes, and the chart is drawn in whole currency units while the tiles keep the exact amount. The best pupils come from `App\Domain\Exams\TopStudents`, which works the averages out of the stored marks exactly as the results page does (whole hundredths, an average that is cut and never rounded, a position from the exact averages, the class stored with the marks), so a past exam always gives the same list. The school has no staff records yet, so a teacher or a staff member on the dashboard is an account with that role. The template's leave requests, notices, events and income/expense widgets are not built because the application holds no such data yet. A read-only school sees a notice on every page.
- **Dashboard submenu.** Like the template, Dashboard in the sidebar opens a submenu: **School** (`/`, everybody) and **Teacher** (`GET /dashboard/teacher`, route `teacher.dashboard`, behind `can:marks.enter`, school address only; the route has its own name so School is not marked active on it). The Teacher page (`TeacherDashboardFigures`) shows the school's student and class counts, the marks this person entered, the open exams, today's attendance (needs `attendance.manage`) and the exams of the current year with links to enter marks or open results. The application does not yet record which classes or subjects a teacher takes, so nothing is filtered by class. The template's **Student**, **Parent** and **LMS** dashboards are not built: there is no link between a user account and a student or guardian yet, and there are no courses.
- **Language.** `SetLocale` (appended to `web`, after the session starts) reads `locale` from the session; `POST /locale` stores it (`config('app.available_locales')`). Everything is translated on the server; the template's client-side `somaplus-i18n.js` and the mock `somaplus-crud.js` are not loaded.
- **Navigation.** `config/menu.php` lists sections and entries (label key, icon, route, optional permission, plan feature, scope and children). `App\Support\Menu` hides an entry whose route does not exist, whose permission the person lacks, whose plan feature the school does not have, or whose scope does not match (school or central address). A parent shows only when a child does. A feature PR adds its menu entry, route, permission and plan feature together.
- **Layout.** A view composer on `layouts.app` supplies the user, the school, the menu and the role label; header, sidebar and footer are our own Blade partials built from the template's markup, with no sample data.

## Academic structure

`App\Domain\Academics` holds the school's calendar and curriculum frame: academic years, terms, classes (`SchoolClass`, the levels), streams and subjects. All five models use `BelongsToTenant`; tables are `academic_years`, `terms`, `school_classes`, `streams`, `subjects` with a `tenant_id` and restrictive foreign keys.

- **Rules** (enforced in the `Save*` actions and by the database): names are unique within the school (terms within their year, streams within their class, subject codes within the school); years of one school never overlap, a term lies inside its year and terms of a year never overlap; a year's terms must stay inside its dates when the year is changed; a school has at most one current year (the action un-marks the previous one, and a partial unique index guards it). Classes are ordered by `sort_order`.
- **Permissions**: `academics.view` (owner, head teacher, teacher, accountant) and `academics.manage` (owner, head teacher), declared in `config/roles.php` and granted to existing schools by a data migration (`SyncTenantRoles`). `AcademicsPolicy` maps the policy abilities to them. The writing routes also use `tenant.writable`. Nothing here is plan-gated, so it works on every plan.
- **Routes and pages** under `/academics` (`routes/academics.php`): years (with their terms), classes (with their streams) and subjects; plain forms, no template JavaScript. The sidebar follows the template: section Academics with Students (Student list, Add student), Academic years and Classes (Class list, Subjects). Route model binding goes through the tenant scope, so another school's record is a 404.
- **Deleting**: `DeleteAcademicRecord` refuses a year that has terms and a class that has streams. History is never removed: features that later refer to these records (students, marks, fees) keep restrictive foreign keys and add their own check to that action.
- The dashboard shows the current year and the term that today falls in.

## Help centre

Help lives inside the application at `/help` (`HelpController`, sign-in required, also on the central address), in the structure of the Odessa POS help centre: categories with an icon, a search box, article pages with a table of contents, the other articles of the category and previous/next buttons, and a contact card for Odessa Lab customer care.

- `config/help.php` holds the categories (key => icon) in display order; a category without articles is not shown. Titles and descriptions are in `lang/{en,sw}/help.php`.
- Articles are Markdown files `resources/docs/{en,sw}/<category>/<slug>.md` with front matter `title`, `summary`, `keywords`, `order`. English is the fallback for an article a language lacks, but a test requires both languages to have the same articles.
- `App\Support\Help\HelpCenter` reads, searches (title 10, keywords 6, summary 3, text 1 points; every word must match) and renders them (`html_input` stripped; each `##` heading gets an id for the table of contents). `[text](help:category/slug)` links to another article.
- Route: `/help/{category}/{slug}`, both parts limited to `[a-z0-9-]+`, so no file outside `resources/docs` can be read.
- An article describes only what the application really does. Every feature adds or updates its articles in both languages.

## Plans and subscriptions

- Plans live in the `subscription_plans` table (`key`, `name`, `features` JSON). `config/plans.php` only seeds missing plans through `PlanSeeder` (`php artisan migrate --seed`); the seeder never overwrites an existing plan, so changing a plan's features needs a data migration.
- Feature keys are added to a plan only when a feature that checks the key exists. For now the three plans (basic, medium, enterprise) have no features.
- A tenant has one plan (`subscription_plan_id`) and a `subscription_status`: `active`, `grace` or `read_only`. A lapsed subscription moves from grace to read-only and never deletes data. Nothing changes the status automatically yet.
- Gating: `plan:<feature>[,<feature>]` route middleware (403 unless the current school's plan has every feature), `Plans::current()->allows('<feature>')` for code outside requests, and the `feature` key in `config/menu.php` (with navigation). With no tenant, nothing is allowed.
- `tenant.writable` route middleware answers 403 to changes (anything but GET/HEAD/OPTIONS) from a read-only school. Routes that change data must use it; login and logout must not.

## Environments

- Local supporting services (PostgreSQL 16, Redis, Mailpit) run from `docker-compose.yml`. PHP and Node run on the host; Laravel Sail is not used.
- Tests run on SQLite in memory.
- CI (`.github/workflows/ci.yml`) is the source of truth for quality gates: Pint, PHPStan level 5, Pest, `composer audit` and `npm run build`.

## Students and guardians

`App\Domain\Students` holds the pupils of a school. Tables: `students`, `guardians`, `guardian_student` (pivot with relationship and main contact), `enrollments` and `audit_logs`; all models use `BelongsToTenant` and every foreign key is restrictive.

- **Students** have a school-unique admission number, names, gender, date of birth, date admitted and a status (`active` or `left`, with the date and a reason). Students are never deleted: they are marked as left and can be brought back.
- **Bulk import** (`GET /students/import`, `/students/import/template`, `POST /students/import`, `StudentImportController`, `App\Domain\Students\ImportStudents`): a CSV (UTF-8 or semicolon, as Excel saves it) with the columns in `ImportStudents::COLUMNS` adds new students, all or nothing. Every row is validated first; any problem refuses the whole file with the line numbers (`StudentImportException`), then one transaction saves each row through `SaveStudent` (audit line, first placement in the current academic year) and `AddGuardian` (one guardian per phone number, main contact). Class and stream are matched by name inside the school and are never created. Existing admission numbers are a problem, never an update, so a repeated file adds nothing. Needs `students.manage`; the POST is behind `tenant.writable`. Limit `config/students.php` (`import_max_rows`). The file is read from its temporary path, not stored, and nothing from it is logged; one `student.imported` audit line is written. It mirrors the product import of Odessa POS, without a spreadsheet package (CSV only), because new PHP packages cannot be installed from the sandbox.
- **Placements** (`enrollments`) are append-only: a promotion or a move adds a row for a year, class and optional stream, and the newest row of a student and year is the one that counts (`CurrentPlacements`). `EnrollStudent` is idempotent (the same placement as the newest one adds nothing) and refuses students who have left. `DeleteAcademicRecord` refuses a year, class or stream that has placements.
- **Guardians** are one record per phone number in a school, so brothers and sisters share it (`AddGuardian`); a guardian left with no student is deleted (`RemoveGuardian`). Only name, phone and optional email are collected.
- **Audit log**: `RecordAudit` writes who did what to which record (`student.viewed`, `created`, `updated`, `placed`, `left`, `reinstated`, `searched`, `guardian.linked`, `guardian.unlinked`). It stores ids only, never names or phone numbers. There is no page for it yet.
- **Privacy**: searching is a `POST` so the typed name never reaches a URL or log; pages use numeric ids only.
- **Permissions**: `students.view` (owner, head teacher, teacher, accountant) and `students.manage` (owner, head teacher), granted to existing schools by a data migration. Parent/student accounts have no access. `StudentPolicy` maps the abilities; writing routes use `tenant.writable`. Routes are in `routes/students.php`; nothing is plan-gated.

## Attendance

`App\Domain\Attendance` holds the daily register. One table, `attendance_records`: one row per student and day (unique `student_id` + `attended_on`) with status `present`, `absent`, `late` or `excused`, an optional note and who recorded it. Each row also keeps the academic year, class and stream the student had that day, so moving a student later never changes old registers. All foreign keys are restrictive; because a row needs a placement, a year, class or stream with attendance is already protected by `DeleteAcademicRecord` through the placements.

- **Roll**: `ClassRoll` lists the active students whose newest placement in the academic year containing the date is the chosen class (and stream). `RecordAttendance` refuses a date outside every academic year, a future date and any student who is not on that roll (so another school's student or a student in another class cannot be marked), and updates existing rows instead of adding duplicates, so a resend or a correction is idempotent. Every save is written to the audit log (`attendance.recorded`, with the class id).
- **Summary**: `AttendanceSummary` counts the statuses per student between two dates. The rate is (present + late) / (present + late + absent); excused days are left out.
- **Permission**: `attendance.manage` (owner, head teacher, teacher) for both looking and saving, granted to existing schools by a data migration; accountants and parent/student accounts have no access. `AttendanceRecordPolicy` maps it; saving uses `tenant.writable`. Routes are in `routes/attendance.php`; class, stream and dates travel in the query string (no personal data). Nothing is plan-gated.

## Exams, marks and grades

`App\Domain\Exams` holds grading scales, exams and marks. Tables: `grading_scales`, `grading_bands`, `exams`, `exam_marks`; all models use `BelongsToTenant` and every foreign key is restrictive. Results, positions and report cards are built on it (below).

- **Marks are exact.** `Score` reads a typed mark (digits, one `.` or `,`, at most two decimals, nothing else) into whole hundredths, so 45.5 is 4550. Nothing is compared as a float. The database holds `decimal(6,2)`.
- **Grades are never stored or typed.** `GradeCalculator` works out the grade from the exam's own grading scale each time it is shown. A scale is a list of bands; a band is the *lowest percentage* that earns its grade, so bands cannot leave gaps or overlap, and the lowest band must start at 0 so every valid score has a grade. The percentage is score / max x 100, compared in integers (`score * 10000 >= minimum * max * 100`), so a score exactly on a boundary gets the higher grade and 79.99 does not.
- **Reproducible.** An exam keeps the scale it was created with (`exams.grading_scale_id`). `SaveGradingScale` and `DeleteGradingScale` refuse to change or remove a scale that any exam uses (checked under a row lock); `DuplicateGradingScale` copies a scale so the copy can change. After marks exist an exam's term, scale and maximum mark cannot change (`SaveExam`). `DeleteAcademicRecord` also refuses a year or term with exams and a subject with marks.
- **Mark entry** (`RecordMarks`): the exam must not be locked (checked again under a row lock), each student must be on the class roll (`ClassRoll`, the newest placement of the exam's academic year, active students only), a score must be 0..max, a student cannot be absent and scored, an empty score keeps what is stored (`0` is a score), and nothing is saved unless every row is valid. There is one row per exam, subject and student, so a resend or a correction updates the row; a concurrent insert is retried as an update. The class and stream at entry time are kept on the row. Extra fields in the request (grade, tenant, entered_by) are ignored: only validated rows are read.
- **Locking**: `LockExam` locks and unlocks an exam (`exams.manage` only). A locked exam accepts no marks, edits or deletion, from anyone.
- **Permissions**: `exams.view` and `marks.enter` (owner, head teacher, teacher), `grades.manage` and `exams.manage` (owner, head teacher); accountants and parent/student accounts have no access. Granted to existing schools by a data migration. Writing routes use `tenant.writable`; a read-only school can look at marks but not save them. Routes are in `routes/exams.php`; class, stream and subject travel in the query string (no personal data). Teachers can currently enter marks for any class and subject; assigning teachers to subjects belongs to the staff feature.
- **Audit log**: `grading_scale.created/updated/deleted`, `exam.created/updated/deleted/locked/unlocked`, `marks.recorded`, `marks.viewed` (ids only).

### Results, positions and report cards

- **Locked exams only.** `ResultSheet` (and `ReportCard`) work from stored marks and the exam's own scale, never store anything, and `ResultSheet` throws for an unlocked exam; the controller shows a notice instead.
- **Totals and averages** are whole hundredths. Absent and empty scores are not counted; `0` is. The average is total / scored subjects, displayed cut (never rounded up) and graded exactly by `GradeCalculator::averageBandIndex` (`total * 100 >= minimum * max * count`), so 79.995 is not an A.
- **Positions** (`Positions::rank`) compare averages by cross multiplication, so equal averages tie (1, 1, 3) and nothing is rounded. Students without a score get none. Class position is across the class; stream position within the stream; filtering by stream keeps class-wide positions.
- **Reproducible.** The class and stream are the snapshot stored on each mark, so a later move or promotion does not change a past result; students who left keep their result. Students placed in the class without marks are listed last.
- **Report card** (`students/{student}/report/{term}`): every locked exam of the term with marks for the student, subject lines with grades, total, average, overall grade, positions. No term-wide aggregate: weighting is a school policy not yet requested.
- **Permission** `results.view` (owner, head teacher, teacher), checked by `ExamPolicy::viewResults` and `StudentPolicy::viewReport`; granted to existing schools by a data migration. GET only, so read-only schools can read. No guardian data is shown.
- **Audit log**: `results.viewed` (exam id), `report.viewed` (student id).

## Fees: structures and invoices

`App\Domain\Fees`. Tables: `fee_structures` (a class in a term), `fee_items`, `invoices`, `invoice_lines`, `document_sequences`; every model uses `BelongsToTenant`, every foreign key is restrictive, and `tenants.currency` (default TZS) is the currency of a school's amounts. Payments, receipts and balances come in the next feature; balances will be derived from payments, never stored on an invoice.

- **Money**: amounts are typed as text and read by `Money::parse` (digits, one `.` or `,`, at most the currency's decimals, at most ten whole digits) into integer minor units; nothing is a float. Display uses `Money::format`.
- **Structures** (`SaveFeeStructure`): the year comes from the term; item names are unique within a structure, amounts above zero. A structure with invoices cannot be edited or deleted (checked under a row lock); `DeleteAcademicRecord` refuses a term or class that has a structure.
- **Invoices** (`GenerateInvoices`): one per student per structure, for the active students on the `ClassRoll` of the structure's class (optionally one stream). Idempotent: students who already have one are skipped, and the DB has a unique key (tenant, student, structure). The generation locks the structure row, copies the lines and total (a snapshot) and records the class/stream at that time.
- **Numbers** (`NextNumber`): a per-school, per-kind counter in `document_sequences`, taken with a row lock inside the transaction that saves the document, so a rollback gives the number back and there are no gaps. The same counter will give receipt numbers.
- **Control number** (`SetControlNumber`): 8 to 20 digits, unique per school (DB unique key), settable and clearable by `fees.manage`. It is the reference a later payment will be matched on; no bank or mobile-money integration exists yet.
- **Permissions**: `fees.view` (owner, head teacher, accountant), `fees.manage` (owner, accountant); granted to existing schools by a data migration. Writing routes use `tenant.writable`, so a read-only school can look but not change. Routes in `routes/fees.php`; filters travel in the query string (term and class ids only).
- **Audit log**: `fee_structure.created/updated/deleted`, `invoices.generated` (only when something was made), `invoice.viewed`, `invoice.control_number_set` (ids only).

## Fees: payments and receipts

`payments`, `receipts`, `payment_reversals` (all `BelongsToTenant`, restrictive keys). A payment is never edited or deleted and never changes an invoice.

- **Balance is derived** (`InvoiceBalance`): paid = sum of the invoice's payments that have no reversal; balance = total - paid; status unpaid / partial / paid / overpaid. Nothing is stored on the invoice.
- **`RecordPayment`** is the one way money is recorded, for the cashier form and for integrations (a later feature will call it with `source = integration`). In one transaction it locks the invoice row, checks the balance, writes the payment and a receipt numbered by `NextNumber('receipt')`, and audits. A person typing a payment cannot exceed the balance; money reported by a provider is always recorded (the invoice may show overpaid).
- **Idempotent**: `idempotency_key` (unique per school; the forms carry a fresh key) and `provider_reference` (unique per school) give back the existing payment; reusing a key or reference for another invoice or amount is refused. The DB unique keys back this up when two requests race.
- **Receipts** are gapless per school (rolled back with the payment if anything fails; refused attempts take no number). **Reversal** (`ReversePayment`, `payments.reverse`, owner only) adds a record with a reason; the payment and receipt stay.
- **Control number**: a payment can be recorded by typing an invoice's control number (looked up inside the school only); the payment keeps a copy of it.
- **Permissions**: `payments.record` (owner, accountant), `payments.reverse` (owner); looking needs `fees.view`. Writing routes use `tenant.writable`.
- **Audit log**: `payment.recorded`, `payment.reversed`, `receipt.viewed` (ids only).

## Settings > Integrations (plug-and-play)

`tenant_integrations` (one row per school and channel: `driver`, `enabled` default false, `settings` json, `secrets` as `encrypted:array`, hidden) and `payment_notifications` (one row per provider reference, `BelongsToTenant`).

- **Pattern (from Odessa-POS)**: `config/integrations.php` lists channels and their driver classes; a driver implements `Driver` (`key()`, `label()`, `fields()` with `secret`, `required`, `generate`, `min`, `options`, `default`). `IntegrationRegistry` lists only channels that have a driver; `IntegrationManager::active($channel)` returns a driver and its decrypted config only when the school's row is enabled and the driver is still offered. Adding a provider = one driver class plus a line in the config; the Settings form is generated from `fields()`.
- **`SaveIntegration`**: needs `settings.manage` (owner). Switching on needs a provider and every required field (a saved secret counts); a blank secret keeps the saved one; changing provider drops the old secrets; a blank `generate` secret is made server-side and shown once in the update response (never in session, DB plain text, audit or logs). Audit `integration.saved` carries the row id only.
- **Payments channel, `signed_webhook` driver**: `POST /webhooks/payments/{tenant}` on the central host only, throttled, no CSRF (`webhooks/*`). The school is named in the path; the body is believed only after `WebhookSignature` (hex HMAC-SHA256 of `"<timestamp>.<raw body>"` with the school's secret, timestamp within 5 minutes, `hash_equals`). Unknown school, switched-off integration or wrong host all answer 404; bad signature 401; malformed signed body 422; otherwise 200 with `{"status": applied|duplicate|unmatched|rejected}`.
- **`ReceivePaymentNotification`** maps a notice to an invoice by control number inside the school and calls `RecordPayment` with `source = integration`, `idempotency_key = provider:<reference>` and `provider_reference`. Every valid-reference notice is kept in `payment_notifications`; an unknown control number is stored as unmatched and re-processed when resent; a currency mismatch or bad amount is rejected; an overpayment is recorded. It runs even for read-only schools (money that moved is never dropped).
- **GePG driver (`gepg`, inbound only)**: built from GePG's *Bill and Payment Information Posting API v4.0* (a public copy; its own text says element names must be confirmed in GePG's test environment). `POST /webhooks/gepg/{tenant}` (central host only, no CSRF, throttled) receives the XML `gepgPmtSpInfo`; `GepgMessage` checks the Base64 SHA1withRSA `gepgSignature` over the exact element text with the school's saved GePG public certificate, requires every `SpCode` to be the school's own, and passes each `PymtTrxInf` (PayCtrNum, PaidAmt, CCy, PayRefId, TrxDtTm) to `ReceivePaymentNotification`. It answers a `gepgPmtSpInfoAck` with code 7101 signed with the school's private key (stored as an encrypted secret) once the notices are kept, so GePG stops resending; a control number no invoice has yet stays listed as "No invoice found" and is recorded by an accountant (Payments > record by control number). Not covered: bill submission/control-number issue, reconciliation and the VPN to GePG (all outbound, needing GePG onboarding); control numbers are typed on the invoice.
- **Selcom driver (`selcom`, C2B collections, inbound only)**: from Selcom's public API reference (the visible text of the C2B section; confirm details in Selcom's sandbox). `POST /webhooks/selcom/{tenant}/{lookup|validation|notification}` (central host only, no CSRF, throttled). Authenticated by the school's bearer token (`hash_equals`; 401 otherwise; 404 for unknown school, off, other provider, wrong host). `utilityref` is the invoice control number; lookup answers 000 with the student's name (the only personal data returned, to an authenticated provider), validation checks the amount with `Money::parse`, notification calls `ReceivePaymentNotification` (reference `SELCOM-<gateway reference>`, method mobile money, currency TZS). Result codes 000 / 010 unknown control number / 012 bad amount / 400 other. Selcom's own outbound APIs (checkout, push USSD, utility payments) are not used.
- **AzamPay driver (`azampay`, mobile money prompt)**: ported from Odessa POS. The school's own AzamPay app (environment, app name, client ID, secret and API key encrypted) is read through `AzamPayClient::forCurrentTenant()` (token and public key cached per school). From an invoice, `RequestMobileMoneyPayment` (`payments.record`, `tenant.writable`, idempotent key, TZS whole shillings, never above the balance) saves a `payment_requests` row (no phone number kept) and asks AzamPay for a checkout. `POST /webhooks/azampay/{tenant}` (central host only, no CSRF) verifies AzamPay's RSA SHA-256 signature over `utilityref + externalreference + transactionstatus + operator` with the public key fetched from AzamPay, then `HandleAzamPayCallback` records the payment through `RecordPayment` (source integration, method mobile money, key `azampay:<reference>`). The signature does not cover the amount, so a success whose amount differs from the request is never recorded (marked failed, `amount_mismatch`); a late success after expiry is recorded (money moved); a repeat is a no-op. Production hosts in `config/azampay.php` must be confirmed with AzamPay at go-live.
- **Bank APIs (NMB, CRDB ...)** have no public documentation here; each is a new driver built from the bank's own documentation, calling the same `ReceivePaymentNotification`/`RecordPayment`.

## Deployment behind Railway's proxy (HTTPS)

Railway ends TLS at its edge and forwards plain http to the container, so without help PHP believes every request is `http://`. `asset()` and `route()` then emit `http://` stylesheet and script links, and the browser blocks them on the `https://` page as mixed content: the page loads with no styling. The template's CSS is static (`public/assets/`, not built by Vite), so the files are fine; only the links were wrong.

- **Trusted proxy** (`bootstrap/app.php`): `trustProxies(at: '*')` for `X-Forwarded-For`, `-Port` and `-Proto` only. The container is reachable only through Railway's proxy. `X-Forwarded-Host` is deliberately not trusted: `ResolveTenant` chooses the school from the request host, and no header may override that (see the tenancy rules in `CLAUDE.md`).
- **Forced scheme** (`AppServiceProvider::boot`): in the `production` environment `URL::forceScheme('https')`, so links built without a request (queued emails such as password reset) are https too.
- **Environment**: set `APP_ENV=production` and `APP_URL=https://<your-domain>` on Railway, and list the Railway/custom hosts in `TENANCY_CENTRAL_DOMAINS` and `TENANCY_BASE_DOMAIN`.
- Tests: `tests/Feature/Shell/HttpsAssetsTest.php`.
